Privacy and Security Statement

Document Version V1.0
October 26, 2026


I. Purpose of the Document

    This document is intended to describe the design principles, implementation mechanisms, and user rights protection measures of the Luna desktop agent software (hereinafter referred to as "Luna" or "this software") in the areas of personal information processing, data storage, network transmission, and permission control.


II. Software Overview

    This software is a desktop personal AI agent running on the Windows operating system. The software uses a capsule-shaped status window that persists at the top of the screen and a main window as its interaction entry points. It can be summoned via global hotkeys or the system tray icon. Users can ask questions to the software in natural language or instruct it to call local tools to complete actual tasks.


III. Overall Principles of Privacy Protection

    This software adheres to the following principles in its design and implementation:

    1. User data is stored on the local computer and is not uploaded to the developer's servers.

    2. Only data necessary for implementing functionality is processed; device information unrelated to functionality, users' routine computer operations, or biometric information is not collected.

    3. Tools are authorized based on risk levels: None/Low tools can be executed directly; Medium/High tools require user confirmation before execution. Only read-only tools on the whitelist allow users to choose "Always Allow (Remember)". High-risk tools (including PowerShell, Python code execution, window management, volume/brightness control, etc.) do not provide an option for permanent confirmation-free execution — each invocation requires manual user approval.

    4. Full Access Mode (see Section 9.5) is a high-risk mode that users proactively enable. This mode only removes the tools' own content restrictions and does not change the authorization rules: Medium/High risk tools still require manual user confirmation. PowerShell and Python code execution still do not provide an "Always Allow (Remember)" option. Once enabled, this feature takes effect globally. Users can manually disable it by clicking the red "⚠ Full Access" marker in the bottom-right corner of the chat area, or via the "Settings - Debug" button to disable Full Access.


IV. Data Processing

    During the user's use of Luna, data manually input by the user or automatically generated by this software may be partially uploaded to remote servers, and partially processed locally on the computer. Details are as follows:

    1. The user's input dialogue content and model responses, session summaries and diary content, uploaded attachments (images, documents, and other files), and long-term facts recorded by the software (such as user preferences) will be sent to the AI provider configured by the user to complete conversations and tasks.

    2. To-do items and reminder times, clipboard text, and screenshot content are only sent together when the model invokes the corresponding tool, the relevant data enters the conversation context, and is transmitted with the request to the AI provider. User configurations such as API Keys and proxy passwords are only sent to the corresponding service providers as request credentials.

    3. In Full Access Mode, AI-generated Python code and PowerShell commands can independently access the network and arbitrary files. In such cases, data transmission no longer passes through this software's network module and does not fall within the scenarios listed in Chapter VI. The software cannot limit, record, or intercept such behavior.

    This software explicitly does not proactively collect or upload the following information:

    Note: The following commitments apply only to this software's own behavior. Data exfiltration initiated by AI-generated code or commands under Full Access Mode constitutes behavior authorized proactively by the user and falls outside the scope of these commitments.

    • Identity information such as users' real names, ID documents, phone numbers, and contact lists;
    • Device and hardware unique identifiers, advertising identifiers;
    • Users' usage behavior and browsing records in other software;
    • Geolocation information;
    • Payment information and bank card information;
    • Any information used for user profiling, advertising, or data trading.

    This software does not integrate third-party analytics SDKs, advertising SDKs, or crash reporting services, and does not contain modules for uploading data to the developer.


V. Local Data Storage

5.1 Storage Locations and Contents

    • Path: %APPDATA%\Luna\settings.json
      Content: Software settings, AI provider information, encrypted API Key
      Description: Keys are encrypted using Windows DPAPI

    • Path: %APPDATA%\Luna\database\LunaData.db
      Content: Sessions, messages, session summaries, diary, long-term facts, to-dos, tool audit records, attachment metadata
      Description: SQLite database, including -wal and -shm auxiliary files

    • Path: %APPDATA%\Luna\database\LunaData.db.before-restore-*
      Content: Database snapshot taken before importing a backup
      Description: Automatically generated when importing data

    • Path: %LOCALAPPDATA%\Luna\blobs
      Content: Raw attachment content
      Description: Named using SHA-256 hashes

    • Path: %LOCALAPPDATA%\Luna\logs
      Content: Runtime logs
      Description: Rotated daily, keeping a maximum of 7 files

    • Path: %LOCALAPPDATA%\Luna\backups
      Content: Automatic backup ZIP files
      Description: Generated daily at 03:00, keeping a maximum of 7 copies

    • Path: %LOCALAPPDATA%\Luna\cache\markitdown
      Content: Temporary cache for document conversion
      Description: Can be safely deleted; will be rebuilt as needed

    • Path: %LOCALAPPDATA%\Luna\.installed
      Content: First-run marker
      Description: Used only to determine whether to display the welcome wizard

    • Path: %APPDATA%\Python\Python3xx\site-packages (actual path varies with the Python version)
      Content: Third-party dependencies installed via pip under Full Access Mode
      Description: Not part of Luna's data directory; uninstalling Luna will not remove them

5.2 Retention Period

    The software does not set a fixed retention period. Data such as sessions, diary entries, to-dos, and long-term facts are managed by the user; once deleted by the user, they are removed from the local database. Logs and automatic backups are automatically cleaned up when they reach their quantity limits (7 each). The Full Access toggle state is saved with settings.json and has no automatic expiration period.

5.3 Storage Security Description

    The database, diary entries, attachments, and logs are all stored in plaintext on the local computer and are not encrypted. The software restricts access through the Windows user account isolation mechanism. Data directories are located only under the current user's configuration directory, and operating system file permissions ensure that other users with general permissions cannot directly read them. Since settings.json and the database are located in the roaming directory %APPDATA%, in enterprise domain environments where roaming profiles are enabled, this data may be synchronized to the domain server along with the user's profile. Attachments, logs, and backups are located in %LOCALAPPDATA% and do not participate in roaming.

    Full Access Mode does not change the storage method described above, but it removes the tool layer's directory and extension restrictions: the AI can read, modify, or delete this software's own data directories (database, logs, attachments, backups, settings.json ciphertext). DPAPI still protects the plaintext of keys, but within the same Windows user context, the ciphertext can be decrypted and used. Account isolation and disk encryption are the primary system-level boundaries in this mode.


VI. Network Transmission and Third-Party Sharing

6.1 Network Access Scenarios

    This software only sends network requests in the following scenarios, all of which are proactively configured or triggered by the user:

    1. Conversation generation: When the user sends a message, dialogue messages, system prompts, relevant long-term facts, and attachment content are sent to the /chat/completions endpoint of the AI provider configured by the user.

    2. Web search: During user-AI interaction, when the AI invokes the search tool, it searches web content through the Tavily search service based on the keywords the user needs to query.

    3. Web page reading: During user-AI interaction, when the AI invokes the web page reading tool, it accesses the specified URL.

    4. News and calendar: During user-AI interaction, when the AI invokes the news and calendar tools, it accesses the corresponding service interfaces. This transmission does not include personal data.

    5. Connection test: When the user clicks "Test Connection" in the welcome wizard or settings, a single minimal conversation request is sent to the currently configured AI service address to verify that the address, model, and key are usable.

    6. Update check: When the user proactively checks for updates, it accesses the GitHub Releases API or releases.atom; after the user confirms the update, the installer and SHA-256 checksum file are downloaded from GitHub Releases.

    7. Proxy connectivity test: When the user clicks "Test Proxy", it accesses https://www.baidu.com through the current proxy, solely to verify that the proxy is usable. No user data is included.

6.2 Network Behavior Under Full Access Mode

    After Full Access is enabled, the code execution tool no longer blocks modules such as socket, urllib, requests, and httpx, and PowerShell no longer restricts verbs such as Invoke-*. AI-generated code or commands can establish arbitrary network connections (including non-HTTP protocols and non-standard ports). Such connections:

    • Do not pass through this software's HttpClient and are not subject to the HTTPS constraints, proxy settings, timeout, or retry policies described in Chapter VII;
    • Do not appear in the network access scenario list in 6.1 and are not audited by this software;
    • May send local file contents, clipboard data, screenshots, and database contents to arbitrary addresses.

    The above behavior is authorized by the user in a one-time consent when enabling Full Access; the software no longer prompts for each individual instance.

6.3 Transmission Security

    Built-in service endpoints (including built-in AI provider presets, Tavily, BBC RSS, and GitHub Releases) all use HTTPS transmission. The HttpClient has not disabled .NET's default TLS certificate validation, and no custom certificate bypass has been implemented.

    • The AI's Base URL is filled in by the user, and the program directly concatenates and requests that address; if an http:// address is provided, conversation content and API Keys will be transmitted in plaintext.
    • The web page reading tool accepts both http:// and https:// addresses; the HttpClient allows automatic redirects by default, and HTTPS pages may be redirected to HTTP.
    • If the user configures an HTTP/SOCKS proxy, network traffic will also be forwarded through that proxy.
    • API Keys are assembled from in-memory plaintext into HTTP request headers before sending. They are not written to logs, but are sent to the service provider configured by the user; confidentiality of the transmission is only ensured when HTTPS is used.

    AI conversation requests set a total timeout, response header timeout, and streaming idle timeout, and retry retryable errors up to 3 times, with a maximum retry wait of 30 seconds. Web search, web crawling, news, update checks, and connection tests each have their own timeouts, but do not uniformly implement the 3-retry mechanism.

    The software does not operate developer-owned relay servers. Except for user-configured third-party services and GitHub update checking/downloading, data is sent directly from the user's local computer to the corresponding service. If the user configures a proxy, requests are forwarded through the user-specified proxy. The developer cannot access data produced by users of this software.

6.4 Third-Party Responsibility Boundary

    The AI providers, search services, websites, GitHub (for update checks/downloads), and proxy test target sites configured by the user are all independent third parties. The collection, storage, and use of data by these third parties is governed by their own privacy policies, over which this software has no control. Luna itself does not provide models; users can select, configure, and use third-party AI services within this software at their own discretion. The compliance responsibility for these services rests with the user and the service providers they choose.


VII. Credential and Key Protection

    The software encrypts sensitive credentials using the Windows Data Protection Interface (DPAPI). The encryption scope includes sensitive strings such as AI service API Keys, Tavily search API Keys, and network proxy passwords.

    • Encryption and decryption: The DPAPI interface provided by the system's crypt32.dll is invoked, with the current Windows user as the protection scope, generating ciphertext that is written to the configuration file in Base64 format. It can only be decrypted by the same Windows user on the same Windows computer; using this ciphertext on other devices or accounts will not yield the correct plaintext. Both encryption and decryption set the CRYPTPROTECT_UI_FORBIDDEN flag to prevent the system from displaying interactive dialogs, thereby avoiding information leakage.
    • On decryption failure, an empty string is returned and treated as unconfigured; no ciphertext or error details are output to the interface.
    • This software provides a data backup feature but explicitly excludes settings.json, preventing encrypted credentials from spreading through backup files.
    • Credentials and key information do not enter logs. Logs only record the request address, model name, HTTP status code, and duration.
    • Under Full Access Mode, the AI can read the ciphertext in settings.json and can call DPAPI to decrypt it within the same Windows user context. It can also read, tamper with, or delete logs, databases, and audit records. Therefore, the strength of credential and audit protection in this mode is lower than in regular mode.


VIII. User Authorization and Permission Control

8.1 Tool Risk Classification

    All tools built into the software declare a risk level, categorized as: None, Low, Medium, and High, accompanied by a "requires confirmation" marker:

    • None/Low: Executed directly;
    • Medium (Dangerous)/High (High-risk): Tools that may read private data, modify the user's computer state, or execute code require user confirmation before execution.

8.2 Authorization Interaction

    Tools requiring confirmation display an authorization dialog before execution, showing the tool name, purpose description, and the actual parameters of the current invocation. The user can make the following choices:

    • Allow once: Approval applies only to this single invocation;
    • Always Allow (Remember): Future invocations of this tool are exempt from confirmation, unless the user executes "Clear allowed authorizations" in the "Tool Authorization" card under "Settings - General". After the user clicks this button, the next invocation of the tool will re-display the authorization dialog. For tools with a higher danger level such as code execution, there is no "Always Allow (Remember)" option — each invocation of such tools requires step-by-step manual approval by the user;
    • Deny: Terminate this invocation and return the denial result to the model.

8.3 Authorization Records

    Tool invocations and authorization results are written to the record table in the local database. Users can review them in the chat history to trace the time, conversation turn, tool name, parameters, and results of each tool invocation.


IX. Tool Execution Security Mechanisms

9.1 Command Execution (PowerShell)

    The control items and their specific implementation methods are shown in the table below:

    ● Control item: Read-only whitelist (regular mode only)
      Implementation: For each pipe-delimited text segment, only checks whether the segment begins with read-only verbs such as Get, Test, Select, Where, Measure, Format, Group, Sort, Compare, ConvertTo, ConvertFrom, Out-

    ● Control item: Write-operation blacklist (regular mode only)
      Implementation: Commands containing verbs such as Remove, Set, New, Invoke, Start, Stop, Restart, Install, Uninstall, Enable, Disable, Clear, Add, Out-File, Set-Content are rejected directly

    ● Control item: Execution environment
      Implementation: Launched with -NoProfile -NonInteractive; user profile is not loaded and interactive input is not accepted

    ● Control item: Timeout control (regular / Full Access)
      Implementation: 30 seconds in regular mode; 60 seconds in Full Access mode, extended to 300 seconds when pip installation is detected; the entire process tree is terminated on timeout or user cancellation

    ● Control item: Output limit
      Implementation: Combined standard output and error output is truncated to 5000 characters to prevent oversized output from overwhelming the interface and context

    ● Control item: Authorization requirement
      Implementation: Risk level High; a confirmation dialog is forcibly displayed for every invocation

    Risk note: The above rules apply only in regular mode and constitute string-level filtering, not PowerShell syntax parsing. Under Full Access Mode, there are no longer any command content restrictions.

9.2 File Read/Write Sandbox

    • Write operations are restricted to the output directory configured by the user in the software. The output directory path is validated through normalization checks to prevent writing outside the directory into system directories via ".." and similar methods. This does not apply in Full Access Mode;
    • The write-extension blacklist covers executable files, scripts, installers, binary files, and image files (such as .exe, .dll, .bat, .ps1, .cmd, .msi, .vbs, .jar, .iso, etc.). Any match is rejected. This does not apply in Full Access Mode;
    • The per-file read limit is 1MB. Files exceeding the limit return an error and are not loaded; under Full Access Mode, this limit is removed, but the 64MB text limit and 100MB document limit still apply;
    • Files read must be genuinely existing files, validated after full path resolution. Unreadable, non-existent, or over-limit files return clear errors without throwing exception details.

9.3 Code Execution Sandbox

    The code execution tool relies on the Python environment on the user's computer, running user- or model-generated Python code in an independent python.exe process. To protect user data security, the sandbox implements the following protective measures:

    • A regex-based blacklist intercepts direct network access (socket, urllib, requests, httpx), process and filesystem operations (subprocess, shutil, pathlib, os, open), and dynamic execution (eval, exec, compile, import) statements. This does not apply in Full Access Mode;
    • Each execution creates an independent random temporary working directory, which is deleted after execution along with the script and directory;
    • Timeout: 10 seconds in regular mode, 60 seconds in Full Access mode, and 300 seconds when pip installation or subprocess is detected;
    • Cumulative output must not exceed 100KB; excess content is discarded and marked as truncated before being returned to the model.

    Risk note: In regular mode, this is a "best-effort" sandbox, not a strong isolation environment. Full Access Mode removes all content restrictions, equivalent to executing arbitrary Python code with the current Windows user's permissions.

9.4 Screen, Window, and System Control

    • The screenshot tool excludes this software's own windows during capture to avoid repeatedly capturing the software interface. On older operating systems that do not support window exclusion, it automatically falls back to a temporary screen-moving solution;
    • Operations such as window management, volume and brightness adjustment are all declared as tools requiring confirmation, displaying the target window or target values before execution;
    • Global hotkeys are implemented through system hotkey registration and a keyboard hook, used only to recognize user-configured key combinations to summon the capsule status window. Key content is not written to the database or logs and is not transmitted over the network.

9.5 Full Access Mode

    Full Access is a global, high-risk switch that must be explicitly enabled by the user, intended to allow the AI to complete tasks that the regular sandbox cannot cover (such as organizing arbitrary directories, installing dependencies, and debugging local programs). The switch state is saved in settings.json and remains effective across sessions and restarts.

    ● Enablement process: Click the "Enable Full Access" button under "Settings - Debug". Three confirmation steps must be completed in sequence: the first explains the three restrictions that will be removed; the second explains the potential system damage, privacy leaks, and financial losses that may result; the third requires the user to manually type "I accept all consequences". After confirmation, the software prompts and automatically restarts, taking effect after the restart.

    ● Restrictions removed: Writing files is no longer subject to the output directory and extension blacklist; the 1MB per-file read limit is removed; Python code execution no longer has network, filesystem, process, or dynamic execution blacklists; PowerShell no longer has the read-only verb whitelist or write-operation verb blacklist.

    ● Mechanisms NOT removed: Tool authorization rules remain unchanged (Medium/High still require confirmation, PowerShell and code execution do not allow "Always Allow", and overwriting existing files requires confirmation); the system-level prompt injection defense specification is still forcibly concatenated; per-invocation timeouts and output truncation remain in effect; DPAPI encryption, TLS validation for the software's own requests, and tool audit logging are all retained.

    ● Disable method: Click the "⚠ Full Access" marker on the capsule status window or the main window, or click "Disable Full Access" under "Settings - Debug". After confirmation, the software automatically restarts and restores regular policies. This switch has no automatic expiration period and must be manually disabled by the user.

    ● Status indication: The capsule window and main window display a red "⚠ Full Access" marker (clickable to disable); the placeholder text in the capsule window input field changes to "Type a message (Full Access enabled)"; the output directory card under "Settings - General" displays "Full Access enabled; tool invocations are no longer subject to this constraint".

    ● Enabling and disabling the switch writes a warning-level local log entry that records only the action and time, without user data.


X. Prompt Injection and Untrusted Content Protection

    During the use of this software, the model uses tool content to feed external content such as web pages, documents, clipboard data, and command output into the model's context. There is a risk of malicious content disguised as instructions, so the software implements the following protective measures:

    • The system-level security specification is forcibly concatenated by the program after the user-configured personality prompt. This specification is hardcoded, and user-customized personality prompts cannot override or delete this portion;
    • Web content, file content, clipboard content, and similar data returned by tools are explicitly defined as "data" rather than "instructions". The system specification requires the model not to execute any instructional text within such content;
    • The set of tools the model can invoke is defined by the program registry; unregistered tools cannot be invoked. Tool parameters are validated by the program before execution, and the model cannot bypass validation to directly manipulate the filesystem or processes;
    • Even if the model is induced to use high-risk tools, user authorization is still required, and in regular mode the whitelist and blacklist also apply.

    Note: Under Full Access Mode, protections still exist, but the consequences are significantly amplified: once the model is induced by web page or file content, it can execute deletion, encryption, exfiltration, and other operations without content restrictions. It is recommended to disable this mode when processing documents or web pages from unknown sources.


XI. Data Integrity Verification and Assurance

    1. SQLite WAL journal mode and foreign key constraints are enabled, and a PRAGMA quick_check integrity check is executed at startup. Exceptions are logged and initialization is terminated to prevent the program from continuing to write in a corrupted state;

    2. Database access is performed through Dapper parameterized statements or fixed SQL; no paths where user input is directly concatenated into SQL were found during review;

    3. settings.json uses a "write temporary file first, then replace the target file" approach; a failed write will not overwrite the source file, avoiding the creation of incorrect configuration files;

    4. A .bak backup is refreshed after each successful load; if the primary configuration is corrupted, it is automatically restored from the backup, with the corrupted file renamed to .corrupt-<timestamp> and saved for diagnostics;

    5. Users can optionally export a backup ZIP file containing diary entries, long-term facts, sessions, messages, to-dos, session summaries, attachment metadata, and attachment files. On import, the software verifies that the backup contains a database file and validates the database structure; otherwise, it is rejected outright. Import operations use a stage-then-overwrite approach to avoid forced overwriting while the program is running. A .before-restore-<timestamp> snapshot file is automatically generated before overwriting; if the overwrite fails, a rollback is attempted. After a successful restore, orphaned attachments that are no longer referenced are cleaned up.

    6. Under Full Access Mode, the AI may directly modify or delete the database, backups, and logs through commands. WAL mode, parameterized queries, and snapshot rollback mechanisms cannot defend against such proactive modifications, and the integrity of audit records consequently degrades.


XII. Logging and Auditing

    During the user's use of Luna, the program writes log entries to log files based on usage scenarios and specific situations, for local troubleshooting and stability improvement purposes. Log files are not proactively uploaded to remote servers by this software.

    Logs record runtime information such as module startup, configuration loading, request addresses and models, HTTP status codes, durations, exceptions, and file paths. Normal paths do not record full conversation content, keys, or file body text; some exception paths record error response fragments returned by the server (up to 500 characters) and file paths for local troubleshooting. Logs are retained on a daily rotation basis, keeping a maximum of 7 files; expired files are automatically deleted.

    Toggling the Full Access switch writes one warning-level log entry. Under Full Access Mode, logs and audit records can be read, tampered with, or deleted by AI-generated commands.

    Tool names, summary of tool invocation parameters, authorization results, execution status, and timestamps are written to the local database and displayed in the corresponding chat history for user self-review.


XIII. Compliance Statement

    1. This software complies with the requirements of the Cybersecurity Law of the People's Republic of China, the Data Security Law of the People's Republic of China, and the Personal Information Protection Law of the People's Republic of China, processing personal information lawfully, legitimately, necessarily, and in good faith;

    2. This software does not proactively collect personal information of minors;

    3. This software does not use user data for advertising, user profiling, or other analytical or data trading purposes;

XIV. Known Limitations and Risk Disclosures

    For the convenience of user evaluation and review, this software truthfully discloses the following limitations:

    1. The local database is not fully encrypted: the database, attachments, and logs are stored in plaintext, with security relying on system-level measures such as Windows account isolation and disk encryption;

    2. Third-party models are uncontrollable: model outputs are generated by third-party services, and the software cannot guarantee their accuracy. Users should independently judge outputs related to important decisions;

    3. The sandbox is best-effort: code execution and command execution employ process-level isolation and rule validation, which are not strong isolation and cannot completely rule out bypass possibilities. Therefore, all such operations require user confirmation each time. There are no sandbox restrictions under Full Access Mode;

    4. Roaming directory risk: in enterprise environments where roaming profiles are enabled, configuration files and the database may be synchronized to the domain server along with the account;

    5. Full Access has no automatic expiration: once enabled, it remains in effect until manually disabled by the user, and the software does not periodically re-confirm;

    6. Full Access does not elevate privileges: it remains subject to Windows user account permissions and UAC constraints; running as a standard user cannot write to protected directories;

    7. pip installation permanently alters the environment: under Full Access, pip install automatically appends --user, installing dependencies into the user-level Python environment, which may affect other Python projects.
