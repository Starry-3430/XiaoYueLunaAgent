Luna Smart Assistant Software V1.0 - Privacy and Security Statement

Document Version V1.0
October 24, 2026


I. Document Purpose

This document describes the design principles, implementation mechanisms, and user rights protection measures of the Luna desktop agent software (hereinafter "Luna" or "the Software") with respect to personal information processing, data storage, network transmission, and permission control.


II. Software Overview

The Software is a desktop personal AI agent running on Windows. It uses a capsule-shaped status window docked at the top of the screen and a main window as its interaction entry points, and can be invoked through a global hotkey or the system tray icon. Users can ask the Software questions in natural language, or instruct it to call local tools to complete practical tasks.


III. General Privacy Protection Principles

The Software follows the principles below in its design and implementation:

1. User data is stored on the local computer and is not uploaded to the developer's servers.
2. Only data necessary to implement the functionality is processed. Device information unrelated to the functionality, users' everyday computer operations, and biometric information are not collected.
3. Tool authorization is controlled by risk level: None/Low tools may execute directly; Medium/High tools require user confirmation before execution. Only read-only tools on a whitelist offer an "Always allow (remember)" option. High-risk tools (including PowerShell, Python code execution, window management, and volume/brightness control) do not offer persistent approval and require manual user approval on every invocation.
4. Full Access mode (see 9.5) is a high-risk mode that the user must explicitly enable. It only removes content restrictions imposed by the tools themselves and does not change the authorization rules: Medium/High risk tools still require manual confirmation, and PowerShell and Python code execution still do not offer "Always allow (remember)". Once enabled, the mode applies globally. The user can turn it off by clicking the red "⚠ Full Access" marker at the bottom right of the chat area, or by using the "Disable Full Access" button under "Settings - Debug".


IV. Data Processing

In the course of using Luna, some of the data manually entered by the user or automatically generated by the Software is uploaded to remote servers, and some is processed locally on the computer. The details are as follows:

1. The user's conversation input and model replies, turn summaries and diary content, uploaded attachments (images, documents, and other files), and long-term facts recorded by the Software (such as user preferences) are sent to the AI provider configured by the user in order to complete conversations and tasks.
2. To-do items and reminder times, clipboard text, and screenshot content are sent to the AI provider configured by the user only when the model invokes the corresponding tool, the relevant data enters the conversation context, and the request is sent.
3. User configurations such as API Keys and proxy passwords are sent to the corresponding service providers only as request credentials.

In Full Access mode, Python code and PowerShell commands generated by the AI can access the network and arbitrary files on their own. In this case, data is sent without passing through the Software's network module and falls outside the scenarios listed in Section VI. The Software cannot restrict, record, or intercept such behavior.

The Software explicitly does not actively collect or upload the following information:

Note: The commitments below apply only to the Software's own behavior. In Full Access mode, data sent out by AI-generated code or commands is the result of the user's explicit authorization and is outside the scope of these commitments.

1. Identity information such as the user's real name, ID documents, mobile phone number, and contacts;
2. Device and hardware unique identifiers, and advertising identifiers;
3. The user's usage behavior and browsing history in other software;
4. Geolocation information;
5. Payment information and bank card information;
6. Any information used for user profiling, advertising delivery, or data trading.

The Software does not integrate third-party analytics SDKs, advertising SDKs, or crash reporting services, and contains no module that uploads data to the developer.


V. Local Data Storage

5.1 Data Storage Locations and Contents

Path	Contents	Notes
%APPDATA%\Luna\settings.json	Software settings, AI provider information, encrypted API Keys	Keys are encrypted with Windows DPAPI
%APPDATA%\Luna\database\LunaData.db	Sessions, messages, turn summaries, diary, long-term facts, to-dos, tool audit records, attachment metadata	SQLite database, including -wal and -shm auxiliary files
%APPDATA%\Luna\database\LunaData.db.before-restore-*	Database snapshot taken before importing a backup	Generated automatically when data is imported
%LOCALAPPDATA%\Luna\blobs\	Original attachment contents	Named by SHA-256 digest
%LOCALAPPDATA%\Luna\logs\	Runtime logs	Rolled over daily, at most 7 files retained
%LOCALAPPDATA%\Luna\backups\	Automatic backup ZIP files	Generated daily at 03:00, at most 7 copies retained
%LOCALAPPDATA%\Luna\cache\markitdown\	Temporary cache for document conversion	Safe to delete; rebuilt on demand
%LOCALAPPDATA%\Luna\.installed	First-run marker	Used only to determine whether to show the welcome wizard
%APPDATA%\Python\Python3xx\site-packages (the actual path varies with the Python version)	Third-party dependencies installed by pip in Full Access mode	Not part of the Luna data directory; not removed when Luna is uninstalled

5.2 Retention Period

The Software sets no fixed retention period. Data such as sessions, diary, to-dos, and long-term facts is managed by the user; once the user deletes it, it is removed from the local database. Logs and automatic backups are cleaned up automatically by count limit (7 files each). The Full Access switch state is saved with settings.json and has no automatic expiry.

5.3 Storage Security Statement

The database, diary, attachments, and logs are all stored in plaintext on the local computer and are not encrypted. The Software restricts access through the Windows user account isolation mechanism. Data directories reside only under the current user's profile directory, and operating system file permissions ensure that other users with ordinary privileges cannot read them directly. Because settings.json and the database are located in the roaming directory %APPDATA%, in enterprise domain environments with roaming profiles enabled, this data may be synchronized to a domain server along with the user profile. Attachments, logs, and backups are located in %LOCALAPPDATA% and do not roam.

Full Access mode does not change the storage methods above, but it removes the directory and extension restrictions at the tool layer: the AI can read, modify, or delete the Software's own data directories (database, logs, attachments, backups, and the encrypted settings.json). DPAPI still protects the plaintext of keys, but within the same Windows user context the ciphertext can be decrypted and used. Account isolation and disk encryption are the main system-level boundaries in this mode.

VI. Network Transmission and Third-Party Sharing

6.1 Network Access Scenarios

The Software sends network requests only in the following scenarios, all of which are actively configured or triggered by the user:

1. Conversation generation: when the user sends a message, the conversation messages, system prompts, relevant long-term facts, and attachment contents are sent to the /chat/completions endpoint of the AI provider configured by the user.
2. Web search: when the AI calls the search tool during interaction with the user, web content is searched through the Tavily search service based on the keywords the user needs to query.
3. Web reading: when the AI calls the web reading tool during interaction with the user, the specified URL is accessed.
4. News and calendar: when the AI calls the news and calendar tools during interaction with the user, the corresponding content service endpoints are accessed. This transmission does not contain personal data.
5. Connection test: when the user clicks "Test Connection" in the welcome wizard or settings, one minimal conversation request is sent to the currently configured AI service address to verify that the address, model, and key are usable.
6. Update check: when the user actively checks for updates, the Software accesses the GitHub Releases API or releases.atom; if the user confirms an update, the installer and SHA-256 checksum file are downloaded from GitHub Releases.
7. Proxy connectivity test: when the user clicks "Test Proxy", the Software accesses https://www.baidu.com through the current proxy solely to verify proxy availability; no user data is included.

6.2 Network Behavior in Full Access Mode

When Full Access is enabled, the code execution tool no longer blocks modules such as socket, urllib, requests, and httpx, and PowerShell no longer restricts verbs such as Invoke-*. AI-generated code or commands can therefore establish arbitrary network connections, including non-HTTP protocols and non-standard ports. Such connections:

1. Do not pass through the Software's HttpClient and are not subject to the HTTPS requirements, proxy settings, timeout, or retry policies described in Section VII;
2. Do not appear in the network access scenario list in 6.1 and are not audited by the Software;
3. May send local file contents, clipboard contents, screenshots, and database contents to arbitrary addresses.

These behaviors are authorized once when the user enables Full Access, and the Software does not prompt for each occurrence.

6.3 Transmission Security

Built-in service endpoints (including the built-in AI provider presets, Tavily, BBC RSS, and GitHub Releases) use HTTPS. The HttpClient does not disable .NET's default TLS certificate validation, and no custom certificate bypass is implemented.

1. The AI Base URL is entered by the user, and the program concatenates and requests that address directly. If an http:// address is entered, conversation content and the API Key are transmitted in plaintext.
2. The web reading tool accepts both http:// and https:// addresses; HttpClient allows automatic redirects by default, so an HTTPS page may also be redirected to HTTP.
3. If the user configures an HTTP/SOCKS proxy, network traffic is additionally forwarded through that proxy.

API Keys are assembled from plaintext in memory into HTTP request headers before being sent and are not written to logs, but they are sent to the service provider configured by the user; confidentiality during transmission exists only when HTTPS is used.

AI conversation requests have an overall timeout, a response-header timeout, and a streaming idle timeout, and retryable errors are attempted at most 3 times with a maximum retry wait of 30 seconds. Web search, web scraping, news, update checks, and connection tests each have their own timeouts, but a uniform 3-attempt retry is not implemented.

The Software does not operate a developer-owned relay server. Except for the third-party services configured by the user and the GitHub update check/download, data is sent directly from the user's local computer to the corresponding service; if the user has configured a proxy, requests are forwarded through that proxy. The developer cannot access data generated by the user's use of the Software.

6.4 Third-Party Responsibility Boundaries

The AI provider, search service, websites, GitHub (update check/download), and the proxy test target site configured by the user are all independent third parties. Their collection, storage, and use of data are governed by their own privacy policies, which the Software cannot control. Luna itself does not provide models; users may independently select, configure, and use third-party AI services within the Software, and compliance responsibility for those services rests with the user and the service provider they choose.


VII. Credential and Key Protection

The Software encrypts sensitive credentials using the Windows Data Protection API (DPAPI). The encrypted scope includes sensitive strings such as AI service API Keys, Tavily search API Keys, and network proxy passwords.

Encryption and decryption: the DPAPI interface provided by the system crypt32.dll is called, and ciphertext is generated with the current Windows user as the protection scope; the ciphertext is written to the configuration file in Base64 form. It can only be decrypted by the same Windows user on the same Windows computer; using the ciphertext on another device or account will not restore the correct plaintext. Both encryption and decryption set the CRYPTPROTECT_UI_FORBIDDEN flag to prevent the system from displaying an interactive prompt and avoid information leakage.

If decryption fails, an empty string is returned and the value is treated as not configured; ciphertext and error details are not displayed in the interface.

The Software provides a data backup feature but explicitly excludes settings.json to prevent encrypted credentials from spreading with backup files.

Credential and key information does not enter logs. Logs record only the request address, model name, HTTP status code, and elapsed time.

In Full Access mode, the AI can read the ciphertext in settings.json and can call DPAPI to decrypt it within the same Windows user context; it can also read, tamper with, or delete logs, databases, and audit records. The protection strength for credentials and auditing in this mode is therefore lower than in normal mode.


VIII. User Authorization and Permission Control

8.1 Tool Risk Classification

All built-in tools declare a risk level: None, Low, Medium, or High, together with a "confirmation required" flag:

None/Low: execute directly;
Medium (dangerous)/High (high-risk): tools that may read private data, modify the state of the user's computer, or execute code require user confirmation before execution.

8.2 Authorization Interaction

Tools that require confirmation display an authorization dialog before execution, showing the tool name, purpose description, and the actual parameters of the current call. The user can choose:

Allow once: approval applies only to this single call;
Always allow (remember): future calls to this tool will not require confirmation, unless the user clicks "Clear allowed authorizations" in the "Tool Authorization" card under "Settings - General". After the user clicks that button, the next call to the tool will show the authorization dialog again. For tools with a higher degree of danger, such as code execution, there is no "Always allow (remember)" option, and the user must manually approve each call;
Deny: terminate the current call and return the denial result to the model.

8.3 Authorization Records

Tool calls and authorization results are written to a record table in the local database. Users can review them in the chat history to trace the time, conversation turn, tool item and parameters, and result of each tool call.


IX. Tool Execution Security Mechanisms

9.1 Command Execution (PowerShell)

The controls and their implementation are shown in the table below:

Control	Implementation
Read-only verb whitelist (normal mode only)	For each text segment separated by |, only checks whether the segment begins with a read-only verb such as Get, Test, Select, Where, Measure, Format, Group, Sort, Compare, ConvertTo, ConvertFrom, or Out-
Write-operation verb blacklist (normal mode only)	Commands containing verbs such as Remove, Set, New, Invoke, Start, Stop, Restart, Install, Uninstall, Enable, Disable, Clear, Add, Out-File, or Set-Content are rejected outright
Execution environment	Started with -NoProfile -NonInteractive; user profiles are not loaded and no interactive input is accepted
Timeout (normal / Full Access)	30 seconds in normal mode; 60 seconds in Full Access mode, or 300 seconds when a pip install --user is detected; on timeout or user cancellation the entire process tree is terminated
Output limit	Standard output and error output are truncated to 5,000 characters in total to prevent excessively long output from overwhelming the interface and context
Authorization requirement	Risk level High; a confirmation dialog is mandatory on every invocation

Risk statement: The rules above apply only in normal mode and are string-level filtering, not PowerShell syntax parsing. In Full Access mode there are no command content restrictions at all.

9.2 File Read/Write Sandbox

1. Write operations are restricted to the output directory configured by the user. The output directory path is normalized and validated to prevent writes outside it (for example, via "..") into system directories. This restriction does not apply in Full Access mode;
2. The write extension blacklist covers executables, scripts, installers, binary files, and disk images (such as .exe, .dll, .bat, .ps1, .cmd, .msi, .vbs, .jar, and .iso). Any match is rejected. This blacklist does not apply in Full Access mode;
3. A single file read is limited to 1 MB; files exceeding the limit return an error and are not loaded. Full Access mode removes this limit, but the 64 MB text limit and the 100 MB document limit still apply;
4. The file to be read must actually exist, and its path is fully resolved and validated; unreadable, missing, or oversized files return a clear error without exposing exception details.

9.3 Code Execution Sandbox

The code execution tool relies on the Python environment on the user's computer and runs user- or model-generated Python code in a separate python.exe process. To protect user data, the sandbox applies the following measures:

1. Direct network access (socket, urllib, requests, httpx), process and file system operations (subprocess, shutil, pathlib, os, open), and dynamic execution (eval, exec, compile, __import__) are blocked by a regular-expression blacklist. This does not apply in Full Access mode;
2. Each execution creates a separate random temporary working directory, and the script and directory are deleted afterwards;
3. Timeout: 10 seconds in normal mode, 60 seconds in Full Access mode, and 300 seconds when a pip install --user or subprocess is detected;
4. Cumulative output is capped at 100 KB; anything beyond that is discarded and marked as truncated in the result returned to the model.

Risk statement: normal mode is a "best-effort" sandbox, not a strongly isolated environment; Full Access mode removes all content restrictions and is equivalent to executing arbitrary Python code with the current Windows user's privileges.

9.4 Screen, Window, and System Control

1. When capturing a screenshot, the tool excludes the Software's own windows to avoid capturing its interface repeatedly; on older operating systems that do not support window exclusion, it automatically falls back to temporarily moving the window off-screen;
2. Window management, volume, and brightness adjustments are all declared as tools requiring confirmation, and the target window or target value is shown before execution;
3. Global hotkeys are implemented through system hotkey registration and a keyboard hook, and are used only to recognize the key combination set by the user to bring up the capsule-shaped status window. Keystrokes are not written to the database or logs and are not transmitted over the network.

9.5 Full Access Mode

1. Full Access is a global, high-risk switch that the user must explicitly enable, intended for tasks that the normal sandbox cannot cover (such as organizing arbitrary directories, installing dependencies, or debugging local programs). The switch state is saved in settings.json and persists across sessions and restarts.
2. Enabling: click "Enable Full Access" under "Settings - Debug". Three confirmation steps are required: the first explains the three restrictions that will be lifted; the second explains the possible system damage, privacy leakage, and financial loss; the third requires the user to type "I accept all consequences". After confirmation, the Software displays a notice and restarts automatically; the mode takes effect after the restart.
3. Restrictions lifted: file writes are no longer limited by the output directory or the extension blacklist; the 1 MB single-read limit is removed; Python code execution is no longer subject to the network, file system, process, and dynamic-execution blacklists; PowerShell is no longer subject to the read-only verb whitelist or the write-operation verb blacklist.
4. Mechanisms that remain: tool authorization rules are unchanged (Medium/High still require confirmation, PowerShell and code execution do not allow "Always allow", and overwriting an existing file still requires confirmation); the system prompt section that guards against prompt injection is still forcibly appended; per-call timeouts and output truncation still apply; DPAPI encryption, TLS validation for the Software's own requests, and tool audit logging are all retained.
5. Disabling: click the "⚠ Full Access" marker in the capsule-shaped status window or the main window, or click "Disable Full Access" under "Settings - Debug". After confirmation, the Software restarts automatically and returns to the normal policy. The switch has no automatic expiry and must be turned off manually.
6. Status indicators: a red "⚠ Full Access" marker is shown in the capsule-shaped status window and the main window (clicking it disables the mode); the placeholder text in the capsule-shaped status window's input box changes to "Type here (Full Access enabled)"; the output directory card under "Settings - General" shows "Full access is enabled; tool calls are no longer restricted by this."
7. Enabling and disabling the switch writes a warning-level entry to the local log, recording only the action and time, with no user data.

X. Prompt Injection and Untrusted Content Protection

During use, the model receives tool content and places external content such as web pages, documents, clipboard text, and command output into the model's context. Malicious content may be disguised as instructions, so the Software adopts the following protections:

1. System-level security rules are forcibly appended by the program after the persona prompt set by the user. These rules are hard-coded, and user-defined persona prompts cannot override or remove them;
2. Web page content, file content, clipboard content, and other tool results are explicitly defined as "data" rather than "instructions"; the system rules require the model not to execute any instruction-like text contained in them;
3. The set of tools the model may call is defined by the program's registry; unregistered tools cannot be called, and tool parameters are validated by the program before execution, so the model cannot bypass validation to operate on the file system or processes directly;
4. Even if the model is induced to use a high-risk tool, user authorization is still required; in normal mode, additional whitelist and blacklist restrictions apply.

Note: In Full Access mode these protections still exist, but the consequences are significantly amplified: once the model is induced by web page or file content, it can perform deletion, encryption, or exfiltration without any content restrictions. Users are advised to turn off this mode when processing documents or web pages from unknown sources.


XI. Data Integrity Verification and Assurance

1. SQLite WAL journaling mode and foreign key constraints are enabled; PRAGMA quick_check is executed at startup for an integrity check. On failure, an error is logged and initialization is terminated to prevent the program from continuing to write in a corrupted state;
2. Database access uses Dapper parameterized statements or fixed SQL; the review found no path that concatenates user input directly into SQL;
3. settings.json is written by "write to a temporary file first, then replace the target file"; if the write fails, the original file is not overwritten, avoiding a corrupted configuration file;
4. The .bak backup is refreshed after each successful load; if the main configuration is corrupted, it is automatically restored from the backup, and the corrupted file is renamed to .corrupt-<timestamp> and kept for diagnosis;
5. Users can export a backup ZIP file containing the diary, long-term facts, sessions, messages, to-dos, turn summaries, attachment metadata, and attachment files. On import, the Software verifies that the backup contains a database file and that the database structure is correct; otherwise the import is rejected. Import uses a stage-then-overwrite approach to avoid forcibly overwriting files while the program is running. A .before-restore-<timestamp> snapshot is generated before overwriting, a rollback is attempted if the overwrite fails, and orphaned attachments that are no longer referenced are cleaned up after a successful restore.

In Full Access mode, the AI may directly modify or delete the database, backups, and logs through commands. WAL, parameterized queries, and snapshot rollback cannot defend against such deliberate modification, and the integrity of audit records is correspondingly reduced.


XII. Logging and Auditing

During use, the program writes log entries to local log files in certain situations for local troubleshooting and stability improvement. Log files are not actively uploaded to remote servers by the Software.

Logs record runtime information such as module startup, configuration loading, request address and model, HTTP status code, elapsed time, exceptions, and file paths. Normal paths do not record full conversation content, keys, or file bodies; some exception paths record an error response fragment returned by the server (up to 500 characters) and the file path for local troubleshooting. Logs roll over daily, at most 7 files are retained, and expired files are deleted automatically.

Toggling the Full Access switch writes a warning-level log entry. In Full Access mode, logs and audit records can be read, tampered with, or deleted by AI-generated commands.

Tool names, summaries of tool call parameters, authorization results, execution status, and time are written to the local database and displayed in the corresponding chat history for user review.


XIII. Compliance Statement

1. The Software complies with the Cybersecurity Law of the People's Republic of China, the Data Security Law of the People's Republic of China, and the Personal Information Protection Law of the People's Republic of China, and processes personal information lawfully, legitimately, minimally, and in good faith;
2. The Software does not actively collect personal information of minors;
3. The Software does not use user data for advertising, user profiling, or data trading;
4. The Software has no account system, does not perform real-name verification, and does not collect any identity document information;
5. If the user configures an overseas AI service provider, relevant conversation content may be transmitted to overseas servers; the Software displays this risk during configuration, and the user chooses independently and bears the corresponding consequences.

Full Access mode is a high-risk feature. The Software obtains the user's explicit consent through three confirmation steps, a clear risk disclosure, and manual entry of a confirmation phrase; this mode is not recommended for minors.


XIV. Known Limitations and Risk Disclosure

To help users evaluate and review the Software, the following limitations are disclosed:

1. The local database is not encrypted as a whole: the database, attachments, and logs are stored in plaintext, and security depends on system-level measures such as Windows account isolation and disk encryption;
2. Third-party models are not controllable: model output is generated by third-party services, and the Software cannot guarantee its accuracy; users should judge outputs used for important decisions themselves;
3. The sandbox is best-effort: code and command execution use process-level isolation and rule validation, not strong isolation, and bypasses cannot be completely ruled out, so every invocation requires user confirmation. Full Access mode has no sandbox restrictions;
4. Roaming directory risk: in enterprise environments with roaming profiles enabled, the configuration and database may be synchronized to a domain server along with the user account;
5. Full Access has no automatic expiry: once enabled it remains in effect until the user disables it manually, and the Software does not periodically ask for confirmation;
6. Full Access does not elevate privileges: it remains subject to Windows user account permissions and UAC, and a protected directory cannot be written when running as a standard user;
7. pip installs persistently change the environment: in Full Access mode, pip install automatically appends --user, installing dependencies into the user-level Python environment, which may affect other Python projects.
