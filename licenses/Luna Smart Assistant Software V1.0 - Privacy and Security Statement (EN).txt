Luna Smart Assistant Software Privacy and Security Statement

October 23, 2026


I. Document Purpose

This document describes the design principles, implementation mechanisms, and user rights protection measures of the Luna desktop agent software (hereinafter "Luna" or "the Software") with respect to personal information processing, data storage, network transmission, and permission control.


II. Software Overview

The Software is a desktop personal AI agent running on the Windows operating system. It uses a capsule-shaped status window docked at the top of the screen and a main window as its interaction entry points, and can be invoked through a global hotkey or the system tray icon. Users can ask the Software questions in natural language, or instruct it to call local tools to complete practical tasks.


III. General Privacy Protection Principles

The Software follows the principles below in its design and implementation:

1. User data is stored on the local computer and is not uploaded to the developer's servers.
2. Only data necessary to implement the functionality is processed. Device information unrelated to the functionality, users' everyday computer operations, and biometric information are not collected.
3. Sensitive operations such as reading from and writing to user computer resources and executing commands are all subject to manual user authorization or manual approval to always allow. High-risk capabilities mandatorily require per-invocation authorization.


IV. Data Processing

In the course of using Luna, some of the data manually entered by the user or automatically generated by the Software is uploaded to remote servers, and some is processed locally on the computer. The details are as follows:

1. The user's conversation input and model replies, turn summaries and diary content, uploaded attachments (images, documents and other files), and long-term facts recorded by the Software (such as user preferences) are sent to the AI provider configured by the user in order to complete conversations and tasks.
2. To-do items and reminder times, clipboard text, and screenshot content are sent to the AI provider configured by the user in scenarios where they are sent together with conversation content.
3. User configurations such as API Keys and proxy passwords are sent to the corresponding service providers only as request credentials.

The Software explicitly does not actively collect or upload the following information:

1. Identity information such as the user's real name, ID documents, mobile phone number, and contacts;
2. Device and hardware unique identifiers, and advertising identifiers;
3. The user's usage behavior and browsing history in other software;
4. Geolocation information;
5. Payment information and bank card information;
6. Any information used for user profiling, advertising delivery, or data trading.

The Software does not integrate third-party analytics SDKs, advertising SDKs, or crash reporting services, and contains no module that uploads data to the developer.


V. Local Data Storage

5.1 Data Storage Locations and Contents

Path	Contents	Notes

%APPDATA%\Luna\database\LunaData.db	Sessions, messages, turn summaries, diary, long-term facts, to-dos, tool audit records, attachment metadata	SQLite database, including -wal and -shm auxiliary files

%LOCALAPPDATA%\Luna\blobs\	Original attachment contents	Named by SHA-256 digest

%LOCALAPPDATA%\Luna\backups\	Automatic backup ZIP files	Generated daily at 03:00, at most 7 copies retained
%LOCALAPPDATA%\Luna\cache\markitdown\	Temporary cache for document conversion	Safe to delete; rebuilt on demand
%LOCALAPPDATA%\Luna\.installed	First-run marker	Used only to determine whether to show the welcome wizard

5.2 Retention Period

The Software sets no data retention period. Data such as sessions, diary, to-dos, and long-term facts is managed by the user; once the user deletes it, it is removed from the local database. Logs and automatic backups retain at most 7 files each; beyond that, the Software automatically cleans up the oldest records.

5.3 Storage Security Statement

The database, diary, attachments, and logs are all stored in plaintext on the local computer and are not encrypted. The Software restricts access through the Windows user account isolation mechanism. Data directories reside only under the current user's profile directory, and operating system file permissions ensure that other users with ordinary privileges cannot read them directly. Because settings.json and the database are located in the roaming directory %APPDATA%, in enterprise domain environments with roaming profiles enabled, this data may be synchronized to the domain server along with the user profile. Attachments, logs, and backups are located in %LOCALAPPDATA% and do not participate in roaming.


VI. Network Transmission and Third-Party Sharing

Network Access Scenarios

The Software sends network requests only in the following scenarios, all of which are actively configured or triggered by the user:

1. Conversation generation: when the user sends a message, the conversation messages, system prompts, relevant long-term facts, and attachment contents are sent to the /chat/completions endpoint of the AI provider configured by the user.
2. Web search: when the AI calls the search tool during interaction with the user, web content is searched through the Tavily search service based on the keywords the user needs to query.
3. Web reading: when the AI calls the web reading tool during interaction with the user, the specified URL is accessed.
4. News and calendar: when the AI calls the news and calendar tools during interaction with the user, the corresponding content service endpoints are accessed. This transmission does not contain personal data.

Transmission Security

All network requests are transmitted over HTTPS, with TLS verification enabled by default by the .NET runtime. Before sending, the API Key is assembled in memory from plaintext into an HTTP request header; it is never written to logs and never leaves plaintext traces.

Requests are configured with timeouts and retry limits (at most 3 attempts, with a maximum retry wait of 30s), to avoid long blocking or repeated sending under abnormal conditions.

No content of the Software passes through any relay server operated by the developer. Data is transmitted directly between the user's local computer and the service provider selected by the user. The developer cannot access any data generated by the user through the use of this Software.

Third-Party Responsibility Boundary

The AI providers, search services, and websites configured by the user are all independent third parties. Their collection, storage, and use of data are governed by their own privacy policies, which the Software cannot control. Luna itself does not provide models; users may independently select, configure, and use third-party AI services within the Software, and compliance responsibility for such services rests with the user and the service providers they choose.


VII. Credential and Key Protection

The Software encrypts sensitive credentials using the Windows Data Protection API (DPAPI). The scope of encryption includes sensitive strings such as the API Key for AI services, the API Key for Tavily search, and network proxy passwords.

Encryption and decryption: the DPAPI interface provided by the system's crypt32.dll is called to generate ciphertext with the current Windows user as the protection scope, and the ciphertext is written to the configuration file in Base64 form. It can only be decrypted by the same Windows user on the same Windows computer; using this ciphertext on another device or account will not restore the correct plaintext. Both encryption and decryption are performed with the CRYPTPROTECT_UI_FORBIDDEN flag set, preventing the system from displaying interactive prompts and thereby avoiding information leakage.

If decryption fails, an empty string is returned and the credential is treated as not configured; neither the ciphertext nor error details are output to the interface.

The Software provides a data backup feature, but explicitly excludes settings.json to prevent encrypted credentials from spreading through backup files.

Credential and key information is never written to logs. Logs record only the request address, model name, HTTP status code, and elapsed time.


VIII. User Authorization and Permission Control

8.1 Tool Risk Classification

All built-in tools declare a risk level: None, Low, Medium, or High, together with a "confirmation required" flag:

None/Low: executed directly;

Medium (dangerous)/High (high-risk): tools that may read private data, modify the user's computer state, or execute code; user confirmation is required before execution.

8.2 Authorization Interaction

Tools that require confirmation display an authorization dialog before execution, showing the tool name, purpose description, and the actual parameters of the current invocation. The user may make the following choices:

Allow this time: approves only this single invocation;

Always allow (remember): exempts future invocations of this tool from confirmation, unless the user performs "Clear allowed authorizations" in the "Tool Authorization" card under "Settings - General". After the user clicks that button, the next invocation of the tool will prompt for authorization again. For code execution tools and other tools of higher risk, there is no "Always allow (remember)" option; every invocation of such tools mandatorily requires manual approval by the user;

Deny: terminates this invocation and returns the denial result to the model.

8.3 Authorization Records

Tool invocations and authorization results are written to a records table in the local database, and users can review them in the chat history to trace the time, conversation turn, tool items and parameters, and results of tool invocations.


IX. Tool Execution Security Mechanisms

9.1 Command Execution (PowerShell)

The control items and their specific implementations are shown in the table below:

Control Item	Implementation
Read-only whitelist	Each pipeline segment of a command must begin with a read-only verb such as Get, Test, Select, Where, Measure, Format, Group, Sort, Compare, ConvertTo, ConvertFrom, or Out-
Write-operation blacklist	Commands containing verbs such as Remove, Set, New, Invoke, Start, Stop, Restart, Install, Uninstall, Enable, Disable, Clear, Add, Out-File, or Set-Content are rejected directly
Segment-by-segment pipeline validation	Each segment is validated separately, with segments separated by |
Execution environment	Started with -NoProfile -NonInteractive; user profiles are not loaded and interactive input is not accepted
Timeout control	A single execution times out after 30 seconds; on timeout or user cancellation, the entire process tree is terminated
Output limit	Standard output and error output are truncated to a combined total of 5000 characters, preventing excessively long output from overwhelming the interface and context
Authorization requirement	Risk level High; a confirmation dialog is forced on every invocation

9.2 File Read/Write Sandbox

1. Write operations are restricted to the output directory configured by the user in the Software. The output directory path is validated through normalization checks to prevent out-of-bounds writes to system directories via means such as "..".
2. The write extension blacklist covers executable files, scripts, installers, binary files, and image files (such as .exe, .dll, .bat, .ps1, .cmd, .msi, .vbs, .jar, .iso, etc.); any match is rejected.
3. The limit for reading and writing a single file is 1 MB; beyond the limit an error is returned and the content is not loaded.
4. Reads must target files that actually exist, and paths are validated after full resolution; unreadable, non-existent, or over-limit cases return explicit errors without exposing exception details.

9.3 Code Execution Sandbox

The code execution tool relies on the Python environment on the user's computer, running Python code generated by the user or the model in a separate python.exe process. To protect the security of user data, the sandbox adopts the following protective measures:

1. A regular-expression blacklist rejects network access (socket, urllib, requests, httpx), process and file system operations (subprocess, shutil, pathlib, os, open), and dynamic execution (eval, exec, compile, __import__) and similar statements;
2. A separate random temporary working directory is created for each execution, and the script and directory are deleted after execution;
3. A timeout limit terminates the process tree if execution exceeds 10 seconds;
4. Cumulative output must not exceed 100 KB; any excess is discarded and returned to the model marked as truncated.

Risk statement: this tool has a high risk level and requires user confirmation. The sandbox is a "best-effort" protection for operating system and data security, not a strongly isolated environment.

9.4 Screen, Window, and System Control

1. The screenshot tool excludes the Software's own window when capturing, avoiding repeated capture of the Software interface; on older operating systems that do not support window exclusion, it automatically falls back to temporarily moving the window off-screen.
2. Operations such as window management, volume, and brightness adjustment are all declared as tools requiring confirmation, and the target window or target value is displayed before execution.
3. Global hotkeys are implemented through system hotkey registration and keyboard hooks, and are used only to recognize the key combination set by the user to invoke the capsule status window. Keypress content is not written to the database or logs and is not transmitted over the network.


X. Prompt Injection and Untrusted Content Protection

While using the Software, the model uses tool content to bring external content such as web pages, documents, clipboard content, and command output into the model's context, creating a risk that malicious content may masquerade as instructions. The Software therefore adopts the following protective measures:

1. System-level security specifications are forcibly appended by the program after the persona prompt set by the user. These specifications are hard-coded, and the user's custom persona prompt cannot override or delete them.
2. Web content, file content, clipboard content, and other content returned by tools are explicitly defined as "data" rather than "instructions", and the system specifications require the model not to execute any instructional text contained therein.
3. The set of tools callable by the model is defined by the program registry; unregistered tools cannot be called, and tool parameters are validated by the program before execution, so the model cannot bypass validation to operate directly on the file system or processes.
4. Even if the model is induced to use high-risk tools, user authorization is still required, and command execution and code execution are additionally restricted by whitelists and blacklists.


XI. Data Integrity Verification and Assurance

1. SQLite WAL journal mode and foreign key constraints are enabled, and PRAGMA quick_check is executed at startup for integrity checking; on anomaly, an error is logged and initialization is terminated, preventing the program from continuing to write in a corrupted state.
2. All database access is performed through parameterized statements or ORM mapping, without concatenating user input, to prevent SQL injection.
3. Settings.json is written using a "write to a temporary file first, then replace the target file" approach; if the write fails, the source file is not overwritten, avoiding a corrupted configuration file.
4. The .bak backup is refreshed after each successful load; if the primary configuration is corrupted, it is automatically restored from the backup, and the corrupted file is renamed to .corrupt-<timestamp> and kept for diagnosis.
5. Users may export backup ZIP files themselves, containing the diary, long-term facts, sessions, messages, to-dos, turn summaries, attachment metadata, and attachment files. On import, the Software verifies whether the backup contains a database file and validates the database structure; otherwise the import is rejected outright. The import operation adopts a stage-first, overwrite-later approach, avoiding forced overwriting while the program is running. A .before-restore-<timestamp> snapshot file is generated automatically before overwriting; if overwriting fails, a rollback is attempted, and unreferenced orphaned attachments are cleaned up after the backup restoration completes.


XII. Logging and Auditing

While using Luna, the program writes log entries to log files in specific situations depending on the usage scenario, for local troubleshooting and stability improvement. Log files are not actively uploaded to remote servers by the Software.

Logs record runtime information such as module startup, configuration loading, request address and model, HTTP status code, elapsed time, and exceptions. They do not record conversation content or keys, and do not record file contents. Logs are retained with daily rollover, keeping at most 7 files; expired files are deleted automatically.

Tool names, summaries of tool call parameters, authorization results, execution status, and timestamps are written to the local database and displayed in the corresponding chat history for users to review.


XIII. Compliance Statement

1. The Software complies with the requirements of the Cybersecurity Law of the People's Republic of China, the Data Security Law of the People's Republic of China, and the Personal Information Protection Law of the People's Republic of China, and processes personal information lawfully, legitimately, minimally, and in good faith.
2. The Software does not actively collect personal information of minors.
3. The Software does not use user data for advertising delivery, user profiling, or other analysis, nor for data trading.
4. The Software has no account system, performs no real-name verification, and collects no ID document information.
5. When users configure an overseas AI service provider, the relevant conversation content may be transmitted to overseas servers. The Software prompts this risk during configuration, and the user makes the choice independently and bears the corresponding consequences.


XIV. Known Limitations and Risk Disclosure

To facilitate user evaluation and review, the Software honestly discloses the following limitations:

1. The local database is not encrypted as a whole: the database, attachments, and logs are stored in plaintext, and security depends on system-level measures such as Windows account isolation and disk encryption.
2. Third-party models are uncontrollable: model output is generated by third-party services, and the Software cannot guarantee its accuracy; users should judge for themselves the output that informs important decisions.
3. The sandbox is best-effort: code execution and command execution use process-level isolation and rule validation, which is not strong isolation and cannot completely rule out the possibility of bypass; therefore, per-invocation user confirmation is required for both.
4. Roaming directory risk: in enterprise environments with roaming profiles enabled, the configuration and database may be synchronized to the domain server along with the account.
